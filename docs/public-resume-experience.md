# 이상민의 경험과 판단 근거

2026-09-08 기준으로 resume 프로젝트의 최신 사실 원장, 개발 철학, 과제 분석,
직접 확인 기록을 대조한 공개용 보강 자료다. 원본의 연락처, 내부 주소, 타인의
커밋 정보, 비공개 이직 사유는 포함하지 않는다. 각 항목은 근거와 한계를 함께 읽는다.
원본 경로는 resume 프로젝트 기준이며, 과제 분석의 실행 결과는 당시 기록이다.

## P01 기술보다 문제와 작은 검증을 먼저 본다

이상민은 사용자가 멈추는 지점과 운영자가 반복하는 일을 문제의 시작으로 본다. AOT 보험 가입 진입에서는 새 프레임워크부터 도입하지 않고 React의 초기 조회 병렬화와 고객 정보 조회 우선순위를 먼저 조정했다. 추가 개선 여지와 낮은 이관 비용을 보고 Next.js·SSR을 선택했다. 기술이 새롭기 때문에 골랐다는 설명과 다르다.

근거: `docs/developer-work-philosophy-v5-2026-07-30.md` §3.1~3.2의 사용자 확인과 경험 해석. 당시 전환은 일괄 교체였고 점진 이관·트래픽 분할 경험은 아니다. 가입 전환율 개선은 측정하지 않았다.

## P02 자동화의 사용자는 실제 업무 담당자다

이상민은 개발자만 실행할 수 있는 자막 CLI로는 운영팀의 업무가 바뀌지 않는다고 보고 다중 파일·다국어 웹 도구로 전환해 백오피스에 편입했다. 무단 유통 도구에서는 반복 검색을 모으되 최종 판단은 운영자에게 남겼다. 운영자도 제품 사용자라는 원칙은 이 경험에서 도출한 해석이다.

근거: `docs/developer-work-philosophy-v5-2026-07-30.md` §4.3, `docs/career-experience-ledger-v9-2026-08-02.md` CCR-05~06. 전문 번역 품질과 불법 여부를 자동 보장하지 않는다. AI 번역 안내 UI는 다른 팀원이 구현했다.

## P03 AI 변경을 검토하고 반영한 책임

이상민은 AI의 대량 파일명 변경에서 일반 구분자 `'.'`가 경로로 잘못 바뀌고 macOS에서 import 대소문자 문제가 드러나지 않았던 실패를 경험했다. 로컬 검증 통과만 보고 push한 자신의 검토 책임을 인정하고 casing 검사와 경로를 보완했으며 후속 리뷰에서 Data Lake 파일명 parsing을 복구했다.

근거: `docs/career-experience-ledger-v9-2026-08-02.md` OPR-04의 코드·Git·사용자 확인. 교훈은 변경 범위를 제한하고 의미 변화를 리뷰하며 실행 환경을 반영해 검증해야 한다는 것이다. 당시 parser 전용 회귀 테스트와 중앙 required check까지 정착시키지는 못했다.

## P04 주도성과 협의형 리딩의 범위

이상민은 미정의 breakpoint·route 접근·오류 문구·ML 취소 기준을 먼저 제안하고 기획·디자인·백엔드와 협의했다. 본인 포함 3명 팀에서 일정·업무 배분·1:1·리뷰를 맡고 막힌 구간을 지원했다. 문제를 결정 가능한 초안과 선택지로 만드는 것이 주도성이라는 설명은 반복 경험의 해석이다.

근거: `docs/developer-work-philosophy-v5-2026-07-30.md` §5.1, `docs/career-experience-ledger-v9-2026-08-02.md` OPR-05. 공식 팀장은 약 6주였다. 모든 변경의 최종 결정자, 조직 전체 리더십, 반대자를 설득한 사례로 확대하지 않는다.

## P05 임시 대응의 한계를 남기는 태도

이상민은 앱 개발 인력이 부족할 때 WebView 키보드 가림을 웹 하단 여백으로 우선 막았고 좋은 장기 해법은 아니라고 인식했다. 모바일 중심 커머스에서는 데스크톱별 화면 확장 공수를 고려해 App-like UI를 선택했다. 현재 제약에서 큰 위험부터 줄이되 임시 대응을 완성된 설계로 포장하지 않는다는 해석이다.

근거: `docs/developer-work-philosophy-v5-2026-07-30.md` §3.2·5.3. 임시 대응의 제거 조건·재검토 시점·소유자를 남기는 것은 이후의 개선 과제이며, 당시에 모두 운영했다는 뜻은 아니다.

## P06 로컬 측정과 실제 환경 확인을 구분한다

이상민은 AOT 전환본의 한국 Desktop Lighthouse LCP 1.2초를 일본 현지 결과로 대신하지 않고 현지 팀원·고객사에 확인했다. 일본 가입 진입 약 5초에서 약 1.2~1.5초는 고객사가 전달한 값이다. 로컬 결과를 가설로 두고 실제 환경을 확인한다는 원칙은 이 경험의 해석이다.

근거: `docs/career-experience-ledger-v9-2026-08-02.md` §2·AOT-02, `docs/developer-work-philosophy-v5-2026-07-30.md` §4.1. 두 측정은 같은 지표·조건의 자체 실험이 아니며, 전환율 상승이나 실사용자 성능 통계로 바꾸지 않는다.

## P07 문서와 실제 API가 다를 때의 확인 순서

이상민은 API 함수나 타입의 존재만으로 연결 완료를 판단하지 않고 service·schema·각 페이지·브라우저 흐름을 대조하려 했다. store에 값이 없으면 실제 API로 복원하고 새 작업·기존 작업·새로고침·직접 진입을 나눠 확인했다. 성공처럼 보이면서 저장·삭제가 되지 않는 상태도 검증 대상으로 봤다.

근거: `docs/developer-work-philosophy-v5-2026-07-30.md` §4.6의 직접 진술과 작업 기록. 문서보다 런타임 확인을 우선한다는 뜻이며 서버 응답을 무비판적으로 신뢰한다는 뜻은 아니다. 작성자와 실행 여부가 불명확한 별도 백엔드 분석은 본인 구현으로 사용하지 않는다.

## P08 지식은 필요한 사람이 쓰는 도구로 전달한다

이상민은 코드 자료에 접근하기 어려운 새 디자이너의 도메인 온보딩 문제를 보고 기획·히스토리 문서를 Markdown으로 옮겼다. 회사 PC의 로컬 LLM Wiki 경험을 바탕으로 의료 도메인 자료를 제공하는 MCP 서버를 만들고 Codex·Claude에서 같은 자료를 참조하도록 연결했다고 확인했다.

근거: `docs/career-experience-ledger-v9-2026-08-02.md` OPR-11, `docs/developer-work-philosophy-v5-2026-07-30.md` §4.5. 사용자 기억이며 MCP 소스·설정·실행 기록으로 재검증하지 못했다. 디자이너의 실제 사용·온보딩 단축, 전사 플랫폼·RAG·자동 최신화·권한 보장을 구현했다는 근거는 없다.

## P09 사실과 해석과 성과를 섞지 않는다

이상민은 기억을 과장해 채우기보다 코드와 Git으로 확인하기를 원했다. 구현의 존재, 선택한 이유, 실제 사용 결과에는 각각 근거가 필요하다고 본다. 주간 고유 이용자는 리텐션이 아니고, 운영팀이 전달한 체감 시간은 통제 실험이 아니다. 검색에서 근거를 찾지 못했다고 경험 자체가 없었다고 단정하지도 않는다.

근거: `docs/developer-work-philosophy-v5-2026-07-30.md` §2·6.1~6.2. 직접 확인 요구와 여러 경험에서 도출한 원칙을 구분한 기록이다. 서로 다른 보험 가입 제품과 고객·계약 운영 제품을 하나의 end-to-end 구현으로 합치지 않는다.

## P10 지식과 사고 방식의 학습을 나눈다

이상민은 좋은 기술 글의 결론만 따라 하기보다 그 사람처럼 생각하려면 무엇을 익혀야 하는지 물었고, 지식과 사고 방식을 나눈 성장 기록을 요청했다. 관찰·가설·작은 실험·실제 환경의 반증·기준 수정 순서는 그 요청에서 도출한 학습 방향이다.

근거: `docs/developer-work-philosophy-v5-2026-07-30.md` §6.4·7의 2026-07-22 직접 요청. 제품 구현 전에 핵심 행동·분모·관찰 기간·실패 이벤트를 정하고 같은 지표로 재검증하는 것은 성장 과제다. 학습 계획과 package manager 비교 기준을 실제 제품 전환 성과로 말하지 않는다.

## E01 오프리메드 백엔드 로그를 업무 데이터와 분리

이상민은 오프리메드 세 백엔드에서 로그용 DB 연결을 업무 데이터와 분리하고 environment·service·request ID로 추적하는 기준을 구현했다. 들어온 요청 ID를 유지하거나 새로 만들고 응답과 로그에 전달했다. 두 제품은 WARNING 이상, Admin은 ERROR 이상 서버 로그를 저장하며 로그 저장 실패가 본 요청을 중단하지 않도록 보호했다.

근거: `docs/career-experience-ledger-v9-2026-08-02.md` OPR-10의 본인 귀속 코드·Git 확인. 각 main 반영과 테스트 코드가 확인됐지만 당시 테스트 재실행, 실제 DB 배포·보존·알림·운영 장애 감소는 확인되지 않았다.

## E02 Admin 로그 조회와 프론트엔드 오류 수집 기반

이상민은 오프리메드 Admin에서 access·application·audit·server 로그 조회와 프론트엔드 오류 보고 API를 구현했다. `service_id + event_id` 멱등성, fingerprint, 전송 제한, 관리자 조회 경계를 두고 로그 DB 연결 누락과 저장 실패를 방어했다.

근거: `docs/career-experience-ledger-v9-2026-08-02.md` OPR-10의 코드·Git·사용자 확인. 이것은 백엔드 수집·조회 기반의 구현 범위다. 각 프론트엔드 sender 연동과 end-to-end 오류 수집, 운영 dashboard·alert·복구 시간 단축은 확인되지 않았다. 타인 작성 변경은 본인 근거에서 제외했다.

## E03 외형과 비시각 접근성을 따로 검증한 경험

이상민은 오프리메드 Portal에서 로그인 오류의 접근성 연결, 서비스 카드 의미 구조, 반복 문구의 접근성 트리 중복, 세션 만료 모달의 배경 inert·Tab 순환·포커스 복원을 보강했다. 기능 검사와 변경 전후 픽셀 비교를 나눠 기존 디자인의 회귀를 확인했다.

근거: `docs/career-experience-ledger-v9-2026-08-02.md` OPR-08. 당시 기록은 Vitest 39개·Playwright 21개·axe 전용 4개 통과와 같은 조건의 8개 화면 RGBA 일치이며 dev 반영까지 확인됐다. WCAG 전체 준수·스크린리더·실사용자 검증이나 운영 배포 결과는 아니다. 대비·좁은 화면·모션 일부는 보류됐다.

## E04 수동 배포를 검증 경로로 옮긴 주도 범위

이상민은 사람이 Docker tar 전달과 서버 기동 순서를 기억하던 배포를 GitHub Actions로 전환하는 작업을 주도했다. 최신 베이스 이력서에는 배포 후 백엔드 HTTP 응답과 컨테이너 상태의 이상을 Actions Summary·로그로 남긴 범위가 명시돼 있다. 변경 전파 누락은 로컬 pre-commit typecheck·pre-push test·build로 확인했다.

근거: `docs/base-resume-final-v62-2026-08-12.md` 경력, `docs/career-experience-ledger-v9-2026-08-02.md` OPR-03. 로컬 Hook은 우회 가능하고 Playwright는 별도 시나리오다. 이전 이미지 재기동을 DB·환경까지 복원하는 완전한 rollback으로 말하지 않는다.

## E05 Playground 제안과 채택 후 구축 책임

이상민은 이벤트·게임 변경이 앱 배포를 기다려야 하는 제약을 보고 WebView Playground를 제안하고 프로토타입으로 시연했다. 채택 후 전용 프론트엔드 프로젝트 구축을 주도하고 운세·이벤트에서 기프트 코드·럭키드로우·설문으로 확장했다. 앱 bridge와 게임 API는 각 담당자와 맞췄다.

근거: `docs/base-resume-final-v62-2026-08-12.md` 코드크레용 경력, `docs/career-experience-ledger-v9-2026-08-02.md` CCR-01. 제안·시연·프론트엔드 구축과 협업의 범위이며 앱·서버 전체를 혼자 구현한 것은 아니다. 게임 주간 고유 이용자 약 2,000~3,000명을 리텐션 상승으로 바꾸지 않는다.

## E06 AX 관심의 구체적인 의미

이상민이 말하는 AX 관심은 추상적인 조직 혁신이나 별도 AI 모델 개발보다 외부 협업 도구·Git·AI 개발 도구를 실제 업무에 연결하는 문제에 가깝다. 요구사항·의사결정·일정·개발 결과의 맥락을 연결해 반복 업무를 줄이는 방식에 관심이 있다고 직접 확인했다. 프론트엔드를 기반으로 API·백엔드·배포·검증까지 역할을 넓히려는 방향과 함께 설명한다.

근거: `docs/lululab-second-interview-motivation-v2-2026-09-04.md` §1~2의 사용자 확인. 관심과 앞으로의 방향이며 Slack·Jira 통합이나 전사 AX를 이미 구축·운영했다는 성과는 아니다.

## W01 요구사항과 완료 기준으로 과제 범위를 정한다

이상민의 웍스피어 채용 파이프라인 보드 과제에서는 필수 흐름과 선택 개선을 나누고 단계마다 목표·완료 기준·테스트 시나리오를 명시하도록 요청했다. 디자인이 주요 요건이 아니므로 shadcn 기본 UI를 적극 활용한다고 직접 이유를 밝혔다. 범위 밖 공고 관리·인증·실제 알림·실제 백엔드는 추가하지 않았다.
